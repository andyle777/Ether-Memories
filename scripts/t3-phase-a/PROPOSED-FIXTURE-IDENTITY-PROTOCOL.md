# Proposed fixture identity and cleanup protocol

This proposal is not an adopted acceptance contract. The current production cleanup is path-based and cannot prove original-object deletion across rename or replacement. `fixtureCleanup` remains PARTIAL.

1. Before actors run, open the owned parent and fixture root with `CreateFileW`, `OPEN_EXISTING`, `FILE_FLAG_BACKUP_SEMANTICS` and `FILE_FLAG_OPEN_REPARSE_POINT`. Reject reparse points and query `FileIdInfo` for both handles. Retain volume serial and 128-bit file ID, and establish the expected parent/child relationship under an explicitly controlled namespace. Handle ownership, access and share modes must be documented and checked.
2. After child termination is independently confirmed, verify the held root identity and the currently named root identity match. Reject a missing root, identity mismatch, wrong volume, reparse point, unexpected entry or failed query. A check followed by pathname deletion is not sufficient: a concurrent replacement can occur after the check.
3. Use an operation bound to the held object for root deletion, such as a suitably authorized `SetFileInformationByHandle(FileDispositionInfo)` on a non-reparse directory handle. Preserve the existing bounded, nonrecursive owned-entry policy. Any child operations still performed by pathname need a separately justified protection against parent or child substitution; merely comparing root IDs does not provide it.
4. Record the disposition request, independently query `FileStandardInfo.DeletePending` while the relevant handle is valid, and close every owned handle. A successful disposition call or a missing pathname alone is not proof that no other handle exists or that every resource is gone.
5. Independently inspect the expected namespace and remaining owned resources after closure, with bounded errors and explicit identity/rename uncertainty. Treat query failures, uncertain containment, unconfirmed children, cleanup errors and incomplete handle accounting as UNVERIFIED. A supported success contract must specify what evidence establishes original-object deletion despite external handles and renames.

The offline probe exercises current-identity NTFS handle observations, not the production cleanup path or cross-identity security. Sharing flags permit other handles to affect deletion; directory deletion may remain pending until the final handle closes. No global race-free or last-handle claim is made.
